# Case Studies

Fifteen documented production deployments. Each entry identifies the use case, the architectural pattern applied, the measured outcome, and the transferable lesson. The cases are drawn from published reports, public earnings calls, and industry research; they are not client-confidential. They serve as the evidence base for the architectural patterns, gate criteria, and sequencing decisions described elsewhere in this playbook.

## Selected Case Narratives

### American Express — IT Helpdesk Automation

American Express deployed a router-worker architecture where incoming IT helpdesk tickets are classified by a lightweight router model (Haiku-class), then dispatched to specialist Workers: a password-reset Worker, a software-provisioning Worker, and an escalation Worker for cases the classifier marks as ambiguous. The Approval Gate required a mandatory HITL gate on any action that modifies access controls, classified as WRITE_INTERNAL risk. End-to-end resolution time for common request types fell by 40%. The key lesson is narrow Worker scope per request type, not one agent attempting to handle the full IT request taxonomy. The classification step is load-bearing: the quality of the router determines the quality of the entire system, because misrouted tickets arrive at Workers that are not equipped to handle them.

### Anthropic — Multi-Agent Research

Anthropic's internal research demonstrated a 90.2% performance improvement on complex research tasks by decomposing them across a Planner and a pool of specialist research Workers. The Planner decomposed the research goal into sub-questions; each Worker executed one sub-question using web retrieval and document synthesis tools; the Planner merged the results. The critical architectural decision was making each Worker's output typed and validatable — the Planner could detect when a Worker produced a low-confidence answer and replan by assigning the sub-question to a different Worker. This is the strongest production evidence for the composition principle: decomposition beats monolith on complex tasks not because the individual models are smarter, but because each agent is scoped to a task it can execute reliably.

### Klarna — Customer Service at Scale

Klarna's customer service agent, built on a router-worker architecture with a strong HITL policy for payment-related actions, handled the equivalent of 700 full-time agents' conversation volume within the first month of deployment. The Approval Gate process for this deployment required a High-risk classification — automated decisions affecting customer financial accounts — quarterly audits, and a mandatory human review path for any dispute or refund over a defined threshold. The architectural lesson is that HITL is not a performance penalty; it is the mechanism that allows a programme to operate at this scale without regulatory exposure. The HITL gates were not designed as an afterthought to satisfy compliance; they were designed as the primary trust mechanism that made the business case viable at all.

### Goldman Sachs — Code Generation at Scale

Goldman Sachs's internal AI platform uses a Worker-pattern code generation agent where the Worker produces code candidates, a separate eval Worker scores them against the team's test suite and style guide, and a human developer reviews the top-scored candidate. The pattern treats code generation as a structured output task with an explicit quality gate, not as a conversational exchange. The programme generated 40% of new code through this pipeline, with human review rate stable at near-100% — the developer's role shifted from writing code to reviewing and approving it. The eval Worker is the architectural element most frequently omitted in comparable programmes: without it, human reviewers are evaluating all candidates with no signal about which is most likely to be correct, which is both slower and less accurate than reviewing a pre-scored candidate.

### Siemens — Maintenance Planning with Graph RAG

Siemens applied Graph RAG to maintenance planning for industrial equipment, where the knowledge corpus is deeply relationship-centric: components have maintenance histories, supplier relationships, replacement part availability, and failure correlations. Standard dense-vector RAG failed to capture these relationships because similarity search treats each document in isolation and cannot traverse the chain of causally related failures that determines the correct maintenance action. The Graph RAG pattern traversed the equipment knowledge graph to surface not just the most similar maintenance record but the chain of related failures and their resolutions. Unplanned downtime fell 25%. The lesson is to choose the retrieval pattern based on the query structure of the use case, not on implementation familiarity. Dense-vector RAG is the correct default for many use cases; it is not the correct default for use cases where the answer depends on relationships between documents rather than on the content of any single document.

## Cross-Case Lessons

**Narrow scope wins.** In every case in this set, the agents that succeeded operated on a well-defined, bounded task. No case involves a general-purpose agent handling an unconstrained domain. The use case scoping discipline described in the Discovery phase exists precisely because production evidence uniformly supports it. Agents that attempt to handle a broad domain exhibit higher failure rates, harder-to-curate eval sets, and more complex HITL policies than agents scoped to a specific request type or workflow stage.

**Invest in evaluation early.** The programmes that scaled successfully all had an eval harness before they had a production agent. The ones that skipped evaluation traded short-term velocity for long-term instability: they shipped faster and then spent the next three months debugging production failures that a golden set of 100 cases would have surfaced before launch. The eval harness is not a quality assurance step applied at the end of the build; it is the specification that defines what the agent must do before anyone writes a line of orchestration code.

**HITL is not a failure mode.** Every high-stakes deployment in this set has a HITL gate. The gate is not evidence that the agent is not good enough; it is evidence that the programme is well-governed. The Klarna case is the clearest illustration: the HITL policy was not a reluctant concession to compliance — it was the mechanism that made the scale of deployment possible. Programmes that treat HITL as a temporary constraint to be eliminated as the model improves misunderstand its function. HITL gates remain appropriate wherever the consequence of an unreviewed error exceeds the cost of the review.

**Model tiering reduces cost by 30 to 70 percent.** Every programme that operated at scale used model tiering: lightweight models for classification and routing, mid-tier for standard tasks, frontier only where the task demonstrably required it. The Shopify case reduced the parameter count from 13B to 7B for cost reasons without sacrificing accuracy on the specific task. The American Express case used a Haiku-class model for the router. Model tiering is not a compromise; it is a design discipline. The correct model for a classification step is the smallest model that meets the accuracy threshold for that step, not the most capable model available.

**Design for collaboration, not replacement.** The programmes with the highest adoption rates framed the agent as a capacity extension for the existing team. The programmes that framed it as replacement experienced resistance that delayed adoption by three to six months. The LinkedIn case is instructive: the outcome communicated to recruiters was not "the agent sources candidates" but "recruiters save one hour per role" — the same fact expressed as a benefit to the practitioner rather than a displacement of the practitioner. The framing of the agent's role is not a communications detail; it is a design decision that determines whether the humans in the system treat the agent as a tool or as a threat.
