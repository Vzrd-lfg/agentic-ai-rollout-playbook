# Agent Security

Agent security is not a separate practice from application security — it extends it. The same principles apply: least privilege, defence in depth, audit everything. What changes is the threat surface: agents have a language model at their core, and that language model can be manipulated. An attacker does not need to exploit a code vulnerability to redirect an agent's behaviour; they need only craft input that causes the model to make different decisions. This possibility does not make agents uniquely dangerous, but it does mean that controls which rely on the predictability of code paths — traditional input validation, static RBAC — are necessary but not sufficient.

## Five-Stage Security Posture

Agent security matures through five stages, each building on the previous. An organisation that has completed Stage 3 but not Stage 1 has policy enforcement with no inventory to enforce against. Stages must be completed in sequence.

```
  Stage 1        Stage 2          Stage 3           Stage 4            Stage 5
  Visibility ──► Identity-First ──► Action Bounds ──► Runtime Def. ──► Detect & Respond
  (inventory)    (per-agent IAM)    (Cedar/OPA)       (injection)       (anomaly alerts)
```

**Visibility.** Before you can secure agents, you must know what agents you have. The AI System Register is the control here. Every agent in production is listed, with its tools, its model, its data sources, and its owner. An agent not in the register should not be in production. In practice, the visibility problem is harder than it sounds: SaaS-embedded agents, endpoint coding assistants, and internally built agents on shared platforms can all accumulate without central coordination. The register discipline must be enforced at the procurement and deployment layer, not just documented as a policy.

**Identity-First Security.** Every agent has a dedicated service identity — an IAM role or equivalent — that is distinct from the identities of the users it serves, the humans who built it, and every other agent in the system. Agents do not share identities. The service identity has the minimum permissions required for the agent's declared tool set; it does not have permissions inherited from a broader role. Identity is verified on every inter-service call. There is no implicit trust within the VPC: an agent calling a tool hosted in the same network segment presents credentials and is authorised at the tool boundary exactly as it would be across a network boundary.

**Action Boundaries.** The Tool Executor enforces a policy on every tool invocation before the call is made. The model cannot instruct the agent to bypass this policy — the policy runs outside the model's context window and is not subject to the model's reasoning. The policy evaluates: who is calling, what are they calling, at what risk class, and on behalf of whom. Cedar and OPA are the canonical implementations. The important property is that the policy is declarative, version-controlled, and testable independently of the agent's prompts. A prompt change cannot widen the action boundary; a policy change can, and that change produces a reviewable diff.

**Runtime Defences.** The primary runtime threats are prompt injection — an attacker embedding instructions in tool output or user input to hijack the agent's behaviour — and privilege escalation — an agent being induced to invoke higher-privilege tools than its task requires. Defences operate at two levels. At the structural level: all tool inputs and outputs are validated against typed schemas before use; retrieved content is treated as data and structurally separated from the model's instruction context; the agent's declared capabilities are not surfaced in user-visible output. At the detection level: injection signatures in retrieved content trigger alerts before the content reaches the model context; tool call sequences that deviate from the agent's established baseline are flagged for review.

**Detect and Respond.** Anomaly signals for agent behaviour include: unusual tool call sequences not present in the evaluation baseline, cross-system access patterns that no single user in the population exhibits, injection signatures in retrieved content, and tool call rate spikes that exceed the agent's established traffic pattern. Alerts generated by these signals route to the on-call engineer. The first response action is the rollback plan tested at Approval Gate check 8: disable the agent without disrupting downstream systems, then begin investigation using the audit log.

## OWASP LLM Top-10 Mapping

The OWASP Top-10 for LLM Applications maps onto the controls already present in the orchestration spine. The table below records which control addresses each threat, so the security review at the Approval Gate can verify coverage systematically rather than ad hoc.

| OWASP LLM Threat | Control in This Architecture |
|---|---|
| LLM01: Prompt Injection | Tool input/output schema validation; retrieved content sanitisation |
| LLM02: Insecure Output Handling | Typed output schema on every Worker; output validated before downstream use |
| LLM03: Training Data Poisoning | Out of scope (no fine-tuning in default architecture); retrieval corpus review process |
| LLM04: Model Denial of Service | Rate limiting at API gateway; timeout and retry policy on every model call |
| LLM05: Supply Chain Vulnerabilities | Approved model list; model provider security assessment; no self-hosted models without review |
| LLM06: Sensitive Information Disclosure | PII detection before model context injection; audit log PII hashing; data minimisation |
| LLM07: Insecure Plugin Design | Typed tool schemas; risk class enforcement; Cedar/OPA policy on every invocation |
| LLM08: Excessive Agency | Narrow Worker scope; max_tool_calls limit; HITL on WRITE_EXTERNAL and IRREVERSIBLE |
| LLM09: Overreliance | Faithfulness eval; citation requirements on RAG responses; HITL on high-stakes decisions |
| LLM10: Model Theft | No model weights stored in application layer; API-only access via PrivateLink/PSC |

LLM03 warrants a note on scope: this architecture consumes foundation models via API and does not perform fine-tuning in the default configuration. If an organisation introduces fine-tuning, training data provenance and attestation become gate requirements and must be added to the AI System Register entry for the resulting model.
